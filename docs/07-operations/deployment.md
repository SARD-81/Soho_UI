# Deployment

This document defines the deployment model and operational requirements for serving SOHO UI as a production static application, with Debian + Nginx as the reference hosting pattern.

It is intentionally a **deployment contract/reference**, not a claim that the repository currently contains automated deployment infrastructure.

At the time of this audit, the repository does not contain:

- `Dockerfile`;
- `.github/workflows/`;
- `nginx.conf`;
- a repository-managed release/deploy script.

Those can be introduced later, but they must preserve the application contracts documented here.

## Deployment model

SOHO UI production build is static:

```text
source
  ↓ npm ci
TypeScript/Vite build
  ↓
dist/
  ↓
Nginx static hosting
  ↓
browser
```

Node.js is required to **build** the frontend, not to serve the generated frontend at runtime when Nginx hosts `dist/`.

## Required artifact

Production web server needs the contents of:

```text
dist/
```

generated by the verified release process in [`build.md`](./build.md).

Do not deploy the source `src/` tree as the web root.

## Build-time configuration must already be correct

Before generating `dist/`, configure the intended production values for:

```text
VITE_API_BASE_URL
VITE_AUTH_API_BASE_URL   optional
VITE_USE_MOCKS=false
VITE_AUTH_BYPASS=false
```

Vite substitutes client environment values at build time.

If an API URL changes after deployment, a previously built artifact will normally need to be rebuilt unless a separate runtime-config architecture is introduced.

## Same-origin versus cross-origin API deployment

Two common deployment topologies are valid.

### Topology A — same public origin with Nginx proxy

Example browser origin:

```text
https://soho.example.com
```

Nginx serves frontend files and forwards `/api/` to the backend.

A build can use the public frontend origin as API base, for example:

```env
VITE_API_BASE_URL=https://soho.example.com
```

The auth base then derives to:

```text
https://soho.example.com/api/auth/
```

Advantages:

- simpler browser CORS model;
- one public TLS origin;
- backend can remain on an internal address/port.

### Topology B — separate API origin

Example:

```text
frontend: https://soho.example.com
backend:  https://api.example.com
```

Build with:

```env
VITE_API_BASE_URL=https://api.example.com
```

and configure backend CORS/authorization headers correctly for the frontend origin.

Use `VITE_AUTH_API_BASE_URL` only if auth is at a different path/origin from the normal backend base.

## Nginx SPA fallback

SOHO uses browser-history routing (`createBrowserRouter`).

A request such as:

```text
/settings
/file-system
/Integrated-space
```

must return the SPA `index.html` when there is no real static file at that path.

Reference Nginx pattern:

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

Without this fallback:

- navigation from inside the SPA may work;
- direct URL entry or browser refresh on a nested route may return Nginx 404.

This fallback is a deployment requirement, not a React Router bug workaround.

## Reference Nginx static server

The following is an illustrative baseline and must be adapted to the actual domain, TLS, paths, backend topology, and organization security policy:

```nginx
server {
    listen 443 ssl http2;
    server_name soho.example.com;

    root /var/www/soho/current;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /assets/ {
        try_files $uri =404;
        expires 1y;
        add_header Cache-Control "public, max-age=31536000, immutable";
    }

    location = /index.html {
        add_header Cache-Control "no-cache";
    }
}
```

This example assumes Vite-hashed files are under `/assets/` and deliberately avoids caching `index.html` aggressively so a release can point users to new hashed assets.

Do not blindly apply immutable caching to unhashed public files.

## Reference same-origin backend proxy

When Nginx also fronts the backend, an illustrative addition is:

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

The exact `proxy_pass` slash behavior matters in Nginx. Validate the resulting backend path rather than copying this template without testing.

Backend address/port and proxy headers are deployment-specific and are not defined by this frontend repository.

## Authentication through a reverse proxy

Verify all of these paths through the deployed proxy/topology:

```text
/api/auth/token/
/api/auth/token/refresh/
/api/auth/token/verify/
/api/system/ui-user/logout/
```

A frontend that can reach ordinary `/api/...` endpoints but not `/api/auth/...` can appear to load normally while login/refresh fails.

## Relative Vite base

Current Vite config uses:

```text
base: './'
```

This produces relative asset references.

Before changing deployment path or adding trailing-slash redirects, verify:

- `/`;
- `/dashboard`;
- `/settings`;
- direct route refresh;
- route URLs with/without trailing slash if the server rewrites them;
- JS/CSS asset URLs;
- fonts;
- 3D/public assets.

Do not change `base` solely to fix an Nginx routing issue without checking SPA fallback and intended hosting path.

## Suggested atomic release layout

The repository does not prescribe filesystem paths, but production deployments benefit from immutable release directories and an atomic `current` pointer.

Example:

```text
/var/www/soho/
├── releases/
│   ├── 20260824-<sha1>/
│   ├── 20260830-<sha2>/
│   └── ...
└── current -> releases/20260830-<sha2>
```

Deployment becomes:

1. upload/extract verified artifact into a new release directory;
2. validate expected files and permissions;
3. atomically switch `current` symlink;
4. reload Nginx only if its configuration changed;
5. perform smoke tests;
6. retain at least one previous known-good release for rollback.

Static application releases do not normally require an Nginx reload when only files/symlink change and the configured root resolves through `current`, but confirm local operational policy.

## Rollback

A static frontend rollback should normally be artifact-based, not a source edit on the production server.

Example concept:

```text
current -> previous known-good release
```

Then re-run smoke checks.

Rollback also needs API compatibility awareness: an older frontend may not be compatible with a newly changed backend contract.

Do not assume frontend artifact rollback is safe if backend schema/API semantics changed incompatibly at the same time.

## File ownership and permissions

Nginx needs read/execute traversal access to deployed static files/directories but should not require write access to the immutable release artifact.

Avoid deployment patterns where the web-server worker can modify application JavaScript or release directories unnecessarily.

Exact user/group values depend on server policy (`www-data` is common on Debian but is not mandated by this repository).

## TLS

Production authentication tokens and sensitive administrative operations require HTTPS.

The application transmits values including:

- Bearer access tokens;
- refresh token during logout;
- passwords;
- filesystem passphrases encoded as Base64;
- network/system administration requests.

Base64 is not encryption. TLS is the transport confidentiality boundary.

Terminate TLS at Nginx or an approved upstream proxy/load balancer and preserve correct forwarded-protocol headers to the backend.

## Security headers

Security-header policy is organization/deployment-specific, but production should evaluate at least:

- `Content-Security-Policy`;
- `X-Content-Type-Options`;
- `Referrer-Policy`;
- clickjacking protection (`frame-ancestors` via CSP or equivalent policy);
- HSTS when HTTPS deployment policy permits it.

Do not introduce an overly strict CSP without testing MUI/Emotion, fonts, Three.js assets, API origins, and any inline/runtime styling behavior.

## Compression

Nginx gzip/Brotli policy can reduce JS/CSS transfer size.

This is a server optimization, not a frontend correctness requirement.

Verify compression with actual response headers and do not compress already-compressed binary formats unnecessarily.

## Cache policy

Recommended conceptual split:

### `index.html`

Short/no cache so new releases are discovered promptly.

### hashed Vite assets

Long immutable cache because the content hash changes with the asset.

### public/unhashed assets

Use a deliberate shorter/version-aware policy; do not assume immutability.

A common broken-release scenario is aggressively cached `index.html` referencing assets that no longer exist or stale HTML preventing clients from discovering the new release.

## Backend availability

Nginx successfully serving the SPA does not prove the application is operational.

Release smoke verification must include actual backend calls such as:

- authentication;
- a monitoring GET;
- a storage/configuration read appropriate for the environment.

## Health checking

Static-file health can check that `/` or `/index.html` returns 200, but a complete system health check should distinguish:

```text
frontend static serving
backend API reachability
auth API reachability
```

Do not use one static 200 response as proof that authenticated API workflows work.

## Release smoke checklist

After switching a release:

1. open `/` and verify SPA boot;
2. verify `/login`;
3. authenticate with an approved test/operator account;
4. open Dashboard and confirm live API data;
5. refresh browser on a nested route such as `/settings`;
6. verify assets/fonts have no 404 in browser network panel;
7. verify API requests target the intended origin;
8. verify auth refresh/normal protected navigation when practical;
9. verify no production mock/auth bypass behavior;
10. perform only safe non-destructive feature reads unless the environment is intended for mutation tests.

## Deployment inputs DevOps needs

For every release handoff provide:

- exact source commit/tag;
- verified `dist/` artifact or reproducible build source;
- Node/npm versions used if DevOps builds it;
- `VITE_API_BASE_URL` value;
- optional `VITE_AUTH_API_BASE_URL` value;
- explicit production values for mock/auth-bypass flags;
- expected public frontend domain/path;
- backend public/internal topology;
- whether Nginx must proxy `/api/`;
- TLS certificate/termination ownership;
- required SPA fallback;
- release/rollback procedure;
- smoke-test result.

No backend/database credential should be handed to the frontend build as a `VITE_*` value.

## What should eventually be automated

A mature deployment pipeline should automate:

```text
checkout exact revision
npm ci
lint
build
artifact packaging/checksum
upload/release directory creation
atomic activation
smoke checks
rollback selection
```

The repository currently has no CI/CD workflow; adding one should be a separate, reviewed infrastructure change rather than undocumented server scripting.
